# Engineering decisions in HouseSync

HouseSync keeps financial authority in one Spring Boot application with PostgreSQL, while a React client handles navigation, user intent and recoverable interactions. These are selected source-backed examples, not a throughput, live-provider or compliance certification. [System overview](architecture/system-overview.md) · [API contracts](index.md) · [testing guide](development/testing.md).

## Exact money and refunds

A transaction carries an explicit currency and decimal-string amount. The backend enforces supported scale and sign at entry, not a JavaScript floating-point approximation ([manual finance contract](architecture/manual-finance-api.md), [ADR 0006](decisions/ADR-0006-manual-finance-contracts.md)). Splits are obligations derived from ledger records, not executed payments.

For an equal allocation, [AllocationSharesPolicy](../backend/src/main/java/com/housesync/finance/transaction/domain/AllocationSharesPolicy.java) converts the positive magnitude to integer minor units exactly once, divides it and distributes leftover units in canonical participant UUID order. A USD 10.00 three-person split therefore conserves every cent as 3.34 + 3.33 + 3.33; it never independently rounds three decimal quotients. Original shares are frozen. For weighted cumulative refunds the `EXACT_JEFFERSON_V1` policy starts from exact integer proportional floors and distributes the remaining minor units by a deterministic priority/tie-breaker; the chosen refund policy is persisted in [V19](../backend/src/main/resources/db/migration/V19__allocation_refund_policies.sql) so history does not silently switch algorithms. [FinancialAllocationService](../backend/src/main/java/com/housesync/finance/transaction/application/FinancialAllocationService.java) validates source, owner, visibility, current roster and version, locks the relevant rows, and commits share/refund changes with replay state in one transaction. A void or correction is retained rather than silently deleting financial history.

**Why this design:** cumulative refunds must never create or destroy a minor unit, and a full refund must reverse the original obligation. The equal-split conversion is bounded by an exact `longValueExact()` call; accepted runtime money ranges must remain aligned with this limit. There is no cross-currency sum or implicit exchange rate. External repayment records attest to a payment outside HouseSync; the app never moves it. Evidence: [policy tests](../backend/src/test/java/com/housesync/finance/transaction/domain/AllocationSharesPolicyTest.java), [allocation HTTP/PostgreSQL integration](../backend/src/test/java/com/housesync/finance/transaction/FinancialAllocationHttpIT.java) and [shared-finance decision](decisions/ADR-0010-shared-finance.md).

## Privacy is a query boundary

Session authentication identifies an actor; it does not grant blanket household-finance access. The [financial account repository](../backend/src/main/java/com/housesync/finance/account/persistence/FinancialAccountRepository.java) joins `household_members` by actor and household **and** filters `financial_accounts.owner_user_id = actor` before paging; detail lookup uses the same scope. The [account service](../backend/src/main/java/com/housesync/finance/account/application/FinancialAccountService.java) checks current membership and returns generic missing-resource behavior for hidden accounts. Household owners have no override to inspect another member’s account. Separately, explicitly shared transactions can be seen by eligible members without granting permission to edit the financial owner’s source or allocation. The backend scopes reports and review records; hiding an account in React would not enforce privacy.

This costs more careful query/service review than a generic repository `findById`, but also limits side channels in list contents and errors. Membership changes must be rechecked on mutation/replay, not treated as a cached frontend role. See [account/transaction contract](architecture/manual-finance-api.md), [privacy decision](decisions/ADR-0006-manual-finance-contracts.md) and [allocation HTTP integration](../backend/src/test/java/com/housesync/finance/transaction/FinancialAllocationHttpIT.java). It is a concrete boundary, not an assertion of a completed external security audit.

## Replay, workers and uncertain writes

A create request can commit on the server while its response never reaches the browser. [FinancialAccountService](../backend/src/main/java/com/housesync/finance/account/application/FinancialAccountService.java) keys idempotency by actor, household, operation and client key; a stored fingerprint rejects key reuse with a different intent, while the account and replay record commit together. Replay looks up the account under current ownership rather than trusting a prior authorization snapshot. Other finance writes follow operation-specific policies; see [API contracts](index.md) for exact scope rather than assuming all endpoints are interchangeable.

Provider synchronization introduces a different race: duplicated demand, worker death and stale results. [V13 sync tables](../backend/src/main/resources/db/migration/V13__slice_b_transaction_sync.sql) constrain one work row per connection, demand/committed sequence order, lease fences and staged rounds, with indexes for due work; the cursor advances only after successfully applied work. [BankActivityService](../backend/src/main/java/com/housesync/finance/activity/application/BankActivityService.java) imposes a consistent lock order for owner-reviewed ledger admission. [AI work](../backend/src/main/java/com/housesync/finance/categorization/application/CategorizationAiWorkService.java) likewise fences stale claims, but AI is optional, off by default and never authoritatively assigns money or categories. [ConnectedFinanceSyncRaceIT](../backend/src/test/java/com/housesync/finance/connection/ConnectedFinanceSyncRaceIT.java) exercises overlapping demands, disconnect and webhook races. This architecture does not promise exactly-once provider delivery or production-grade live bank coverage: repeated delivery must have an explainable outcome, and live bank-initiated changes/removals still need validation.

The frontend does not convert an uncertain network outcome into a success or blindly generate a fresh create request. [FinancialAccountsSection](../web/src/finance/FinancialAccountsSection.tsx) and [BankActivitySection](../web/src/finance/BankActivitySection.tsx) preserve request intent/key across in-page timeout or unknown outcome, allow an explicit same-key retry and refetch authoritative versions on conflict. A list containing a similar account cannot prove which unknown create succeeded because duplicate names are allowed. Keys/drafts are intentionally **memory-only**: a page reload loses them, so the UI does not fabricate a retry after reload. [AuthSection](../web/src/auth/AuthSection.tsx) uses request abort/operation ownership so stale bootstrap or focus rechecks cannot overwrite a later foreground login/logout; [App](../web/src/App.tsx) owns URL-driven navigation and focus changes. Evidence: [bank-activity interaction tests](../web/src/finance/BankActivitySection.test.tsx) and [auth race tests](../web/src/auth/AuthSection.test.tsx).

## What remains difficult

The modular monolith keeps transaction boundaries and access reviews in one place, at the cost of some large application controllers/components and expensive cross-domain review. Those areas deserve decomposition along **existing** use cases when change pressure justifies it, not a speculative microservice layer. Container/PostgreSQL integration and interaction tests give more relevant evidence than a health probe, but do not demonstrate scale, performance, complete accessibility, operational recovery or legal clearance. Optional Plaid and AI require explicit credentials/approval and separate real-provider verification. A public hosted service and native Android app are out of scope; see [known limits](product/known-limits.md) and [deployment](development/deployment.md).
